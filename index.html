CASE STUDY 01

Zenora — full-stack CRM & business platform

FOR A CLEANING & FACILITY-MANAGEMENT BUSINESS

The backend, the database, and the site — all mine

Solo build — backend architecture, database design, multi-tenancy, deployment, and the public site.
zenoraservices.com ↗

Zenora runs an actual cleaning-services business in Accra today: lead intake, quoting, invoicing, job scheduling and reporting, on one shared platform designed to support more tenants than just this one client. I designed the backend as a modular monolith on NestJS rather than reaching for microservices by default — clear module boundaries now, with a defined path to split out services later if one module's load actually demands it.

What I built

  • Multi-tenant data model on a shared MySQL schema, tenant-scoped through companyId relations enforced at the data-access layer.
  • JWT auth with role + tenant authorization — every request checked against both who the user is and which company they belong to, down to which dashboard a role even sees.
  • Full CRM workflow: leads → quotations → jobs → invoices → reporting, plus a live pricing calculator with its own crew-sizing and add-on logic.
  • Automated email workflows via Resend for quote-sent and quote-accepted events.

Architecture notes

  • NestJS + Prisma, controller–service–repository layers kept strictly separate per module.
  • Deliberately a monolith, not microservices — single team, single deploy, one client at launch. Documented the module boundaries so a heavy one (billing, say) can be pulled out later without a rewrite.
  • Deployment: NestJS API on Railway, React frontend on Vercel, MySQL managed separately.
  • Maintained architecture docs covering schema, auth flow, and tenancy model for future contributors.

CASE STUDY 02

Inventiq — inventory & margin intelligence

PERSONAL PROJECT — SMALL-BUSINESS INVENTORY

Cost-per-unit, break-even, and P&L — computed, not guessed

Solo build — API, auth, data model, analytics engine, and an AI insights service.

Built for small producers who sell physical goods and have no real visibility into whether a product is actually profitable. You record what you spent making a batch and how many units it produced; Inventiq derives cost-per-unit automatically, then rolls that into live margin, break-even, and profit-and-loss figures as sales come in — no spreadsheet, no manual recalculation.

What I built

  • Batch-based costing: record what a production run cost and how many units it made; cost-per-unit and margin are derived, never hand-entered.
  • Break-even tracker per product, computed against recorded overhead expenses.
  • Full P&L — revenue, COGS, gross profit, operating expenses, net margin — generated from sales, batches and expense records.
  • JWT-authenticated multi-user accounts with a registration flow, no seeded logins.

Architecture notes

  • React + Vite frontend, Express + Mongoose API, MongoDB for products, batches, sales and expenses.
  • Analytics computed server-side from raw transaction data — never cached numbers that can drift from the source.
  • An AI insights service wired into the backend against the Anthropic API — natural-language queries over the business data, currently server-side and next up for the UI.
  • Runs locally today; not yet deployed publicly.
